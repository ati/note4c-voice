# Note4C: тест добавления чёрных линий

Отдельная прошивка для Zectrix Note4C / HE042A268, 400 × 300, ESP32-S3
N16R8. Проверяет, ограничивает ли команда SSD2683 `0x83` физическое
обновление узкой полосой при использовании штатной цветной OTP.

11 октября 2026 пользователь самостоятельно загрузил тест на устройство и
подтвердил результат: чёрные линии добавляются, мигания происходят **только
на обновляемом участке экрана**. Таким образом, частичное физическое
обновление с цветной OTP подтверждено для этого теста на данном Note4C.
Мигание внутри окна сохраняется; полностью без мигания тест не работает.
Источник результата — визуальная проверка пользователя, не USB-журнал.

Проверенный образ: `dist/firmware.bin`, SHA256
`56cc897f8e3cb6d2e55171163f9d0f23d1b0e537aa425450e846ded8dab857e8`.
11 октября 2026 метод перенесён в основную Voice-прошивку: `src/panel.cpp`
и `src/epd.cpp` в корне проекта. Основное приложение добавляет зачёркивание
2 px; интеграция собрана, проверена программно и загружена на устройство.
Первый запуск и цикл обновления подтверждены USB-журналом; проверка новых
сочетаний кнопок и полос 2 px на панели ещё предстоит. Данный эксперимент
с полосами 8 px сохранён отдельно.

## Управление

1. После включения экран полностью заливается жёлтым. При этом обычное
   мигание ожидается. Дождитесь окончания обновления и выключения LED.
2. Нажмите переднюю круглую кнопку: выполняется попытка добавить чёрную
   горизонтальную полосу толщиной 8 пикселей.
3. Следующее нажатие добавляет вертикальную полосу. Направления чередуются;
   каждый раз используется новое место. Всего 10 полос, затем тест ждёт.
4. Боковая **Up** очищает тест: выполняет полное обновление жёлтым и
   начинает счёт полос заново. RESET также перезапускает тест.

Нажатия во время обновления игнорируются. Удержание кнопки не повторяет
операцию; после обновления нужно отпустить её и нажать снова.
Wi-Fi не используется. Тест остаётся активным, в глубокий сон не входит.
Питание панели отключается после каждой операции, включая ошибки.

Через USB 115200 доступны команды `n` — следующая полоса, `y` — полное
обновление жёлтым, `?` — справка. Журнал выводит координаты, команды SPI,
длительность BUSY и результат выполнения команд. После ошибки дальнейшие
полосы заблокированы до явного восстановления фона кнопкой Up / командой `y`.

## Что наблюдать

- Появилась ли чёрная полоса в ожидаемом месте?
- Мигал ли экран **вне полосы**? Следите за всей панелью, включая углы.
- Сохранился ли жёлтый фон, особенно вокруг полосы?
- Остались ли предыдущие полосы и их пересечения?
- Сколько длилась операция по журналу?

`COMMAND_CYCLE_COMPLETE` означает только завершившийся цикл BUSY. Оптический
результат оценивается визуально: чёрная полоса, сохранённый фон и отсутствие
мигания вне выбранной области. Мигание внутри самой полосы возможно.
Если мигает весь экран, этот способ не выполняет условие частичного обновления.
Если полосы нет, это также отрицательный результат данного способа.
Отрицательный результат не исключает другого режима или специальной LUT.

## Как устроен эксперимент

Фон выводится проверенной последовательностью Note4C из основного проекта:
сброс, `E9 01`, запись 30000 байт через `10`, включение `04`, обновление
`12 00`, выключение `02 00`, сон `07 A5`.

При добавлении полосы:

1. В памяти ESP32 сохраняется весь ожидаемый рисунок с предыдущими полосами.
2. После сброса весь рисунок записывается в RAM контроллера **без запуска
   обновления**, чтобы данные за пределами полосы были определены.
3. Команда `83` получает 9 байт: `x0_hi x0_lo x1_hi x1_lo y0_hi y0_lo
   y1_hi y1_lo 01`. Конечные координаты включительные: `x1 = x0 + w - 1`,
   `y1 = y0 + h - 1`; начало X и ширина выровнены по 8 пикселям.
   Через команду `10` в окно записывается чёрный цвет `00` в штатном
   двухбитном формате BWRY.
4. После включения `04` выполняется **один** запрос обновления `12 00`
   с ожиданием BUSY, затем выключение `02 00`, сон `07 A5` и отключение
   питания панели. Автоматического перехода к полному обновлению при
   неудаче нет.

Полная передача RAM не означает полного физического обновления. По проверке
пользователя, при этой последовательности физическое обновление и мигание
ограничены выбранным окном. Используется штатная цветная OTP (`E9 01`),
без внешней LUT и изменения напряжений. Реализация:
[`src/probe.cpp`](src/probe.cpp), `Panel::addLine()` / `writeWindow()` / `drive()`.

Формат оконной команды взят из
[эталонного драйвера SSD2683 Zectrix](https://github.com/itopinion/zectrix-note4-epd-demo/blob/main/components/zectrix_epd/zectrix_epd.cc),
функции `SetPartialWindow` / `zectrix_epd_refresh_partial_1bpp` (просмотрено
11 октября 2026). Эталон рассчитан на чёрно-белый Note4; применение формата
окна с цветной OTP проверено отдельно этим тестом на Note4C. Монохромные
коды переходов, настройки напряжений и внешние LUT эталона в тесте
не используются.

## Сборка и проверки

Из корня `note4c-voice`, с установленным PlatformIO (см. основной README):

```bash
pio run -d experiments/partial-lines
python3 experiments/partial-lines/tools/check.py
```

Проверки выполняют настоящий код эксперимента с ASan/UBSan и записывающим
транспортом: геометрию и пиксели десяти полос, сохранение жёлтого фона,
SPI-пакеты, ровно один запуск обновления на полосу, отключение питания
при ошибках и обработку кнопки. Они не измеряют физическую панель.

11 октября 2026: сборка PlatformIO — SUCCESS, проверки ASan/UBSan — PASS.
`firmware.bin`: 270992 байта. Проверены SHA256 всех артефактов, сегменты
объединённого образа и совпадение таблицы разделов с рабочей Voice-прошивкой.

Артефакты создаются только в `experiments/partial-lines/dist/`:
`firmware.bin`, `note4c-partial-lines-merged.bin`, сегменты и `SHA256SUMS`.
Сборка не запускает загрузку на устройство.

## Установка и возврат

При прежней таблице разделов установка приложения сохраняет Wi-Fi/NVS.
Команда из корня `note4c-voice`; порт нужно сверить с подключённым устройством:

```bash
python -m esptool --chip esp32s3 \
  --port /dev/cu.usbmodemXXXX --baud 460800 write_flash \
  0xe000 experiments/partial-lines/dist/boot_app0.bin \
  0x10000 experiments/partial-lines/dist/firmware.bin
```

Здесь `boot_app0.bin` выбирает первый раздел приложения; NVS по адресу
`0x9000` не затрагивается. Объединённый образ записывается с `0x0` и
перезаписывает область NVS, поэтому для проверки удобнее отдельные сегменты.

Для возврата к голосовым заметкам соберите основную прошивку и запишите
её сегменты `boot_app0.bin` и `firmware.bin` по тем же адресам
(см. основной README).

Сборка этого эксперимента не изменяет основную Voice-прошивку и её `dist/`.
